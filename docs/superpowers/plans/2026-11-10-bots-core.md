# Bot Page Core Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Group rounds that always finish and show their files, a Bot page that looks and moves like the home chat, memory that keeps up, and the core safety gaps closed (spec A, plus the suggested-models notice, spec A §E).

**Architecture:** A group round becomes segments over a durable `bot_groups.pending` record written after every batch; a segment near its deadline chains the next one through an internal route (CRON_SECRET), and the heartbeat resumes any segment that was killed. The page streams the segment it started and polls a `live` route otherwise. Memory gains pin, recall, soft delete, per-turn rollback, a per-conversation snapshot, and a periodic review on the free Auto model. Every bot turn carries a server-set `origin`.

**Tech Stack:** Node 22 ESM, Express, Postgres (pg; pglite in tests), vanilla JS front end, the repo's `check()` test harness, Playwright UI tests.

**Spec:** `docs/superpowers/specs/2026-11-10-bots-core-design.md`.

## Global Constraints

- Schema version **44**; finance (built in parallel) takes 45 — never depend on 45.
- Every route scoped to the account; another account's id answers 404.
- Every new string in vi and en; `test/i18n.test.mjs` and `test/server-i18n.test.mjs` pass.
- The hand-off ceiling stays 6 per person message across all segments; at most 8 segments per person message.
- No model call the person did not cause, except: chained segments of work they asked for, and the memory review every 20 turns (Off/20/40, default 20) on the free Auto model.
- Bot chat = home chat: change chat behaviour once in the home chat; never build a second composer.
- Browser suites: `test/ui-bots.test.mjs` (5235) and `test/ui.test.mjs` (5194) only from this checkout; never while another checkout runs them.

### Task 2: Rounds as segments (A0.1, A.2, A.3, A.4)

**Files:** `server/bots/rounds.js`; Test `test/bots.test.mjs`.

**Produces:** `runGroupRound({ user, groupId, text, emit, signal, deadlineAt, runAgent, origin, model, resume = false, chain = null })` — `resume: true` runs from `pending` without a new person line; `chain(userId, groupId)` is called (once) when the segment saves `pending` for time. Returns `{ stopReason: 'end_turn'|'time'|'handoff_ceiling'|'aborted'|'segments', turns, handoffs, pending: boolean }`.

Rules (each a failing test first, with a fake `runAgent`):
- `pending` saved after every batch: `{ messageId, queue, handoffs, segments, model, reason, working, at }`; cleared at the natural end.
- Time: saves `reason:'time'`, calls `chain` once, posts no notice (the work continues); on `segments >= 8` posts "Đã làm lâu — bấm Tiếp tục để làm tiếp" (`notice:'segments'`) and saves `reason:'ceiling'`-like `'segments'` for Continue.
- Ceiling: notice `ceiling` with a Continue action, `pending.reason = 'ceiling'`.
- A member cut off mid-turn (signal from the deadline while its turn ran, detected by its chat's last message being an assistant message with tool calls and no final text, or a tool message last): its queue item keeps `resume: true`; the next segment calls `runAgent` on its chat without appending a round prompt.
- Model: before each batch, `group.model` (if set) wins over the request's.
- Person lines mid-round: before each batch, `messagesSince(log, lastSeq)` user lines are queued (admin or named), uncounted.
- The asker always gets its report turn, with `answered`, `passed`, `failed` names; if only the admin was called and it passed: notice `nobody`.
- `markGroupSeen` only after a member turn that ended without error or abort.
- `pending.working` updated at member start/tool/end (for the live route).

- [ ] Steps: tests → implement → `node test/bots.test.mjs` → commit `feat(bots): a round runs in segments that finish what was asked`.

### Task 3: Routes for continue, live, model, internal chain, heartbeat

**Files:** `server/routes/bots.js`, `server/app.js` (internal route + heartbeat phase), new `server/bots/continue.js` (`continueGroup({ userId, groupId, budgetMs })`, `chainNext(userId, groupId)`); Test `test/bots.test.mjs`.

- `POST /bot-groups/:id/run`: no 409 when running — the line is stored (and the running segment picks it up); answers `{ joined: true }` as JSON when another segment holds the lease.
- `POST /bot-groups/:id/continue`: runs from `pending` (any reason), streamed like `/run`.
- `GET /bot-groups/:id/live?since=<seq>` → `{ running, messages: [after since], working: [...], pending: { reason } | null }`.
- `PATCH /bot-groups/:id/model { model }`.
- `POST /api/internal/bot-rounds/continue { userId, groupId }` — `requireCron`; answers 202 and runs `continueGroup` under `waitUntil`.
- `chainNext`: `waitUntil(fetch(publicUrl + '/api/internal/bot-rounds/continue', { method: 'POST', headers: { authorization: 'Bearer ' + CRON_SECRET, 'content-type': 'application/json' }, body }))`; locally (no serverless) it calls `continueGroup` directly on the next tick.
- Heartbeat: `resumeGroupRounds({ budgetMs: remaining() })` after `resumeCutOffTurns`.
- [ ] Steps: tests (fake fetch for chain; stale group resumed by heartbeat; 8-segment cap) → implement → commit `feat(bots): rounds carry on in a new invocation, and the heartbeat picks up a killed one`.
