# Diagrams that come out right — implementation plan (1.34.0)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Boxes-and-arrows drawings come out right. The server lays them out from a structured `diagram` input, so arrows connect by construction. A hand-written SVG is checked for lines and arrows too, and when it is flawed it is redrawn once, unseen. A built-in skill tells every model how to draw and how to make pictures.

**Architecture:**
- A pure layout engine (`server/diagram/`: validate → layout → render) turns `{ direction, nodes, groups, edges }` into SVG with a layered (Sugiyama-style) layout and orthogonal edge routing.
- `server/widgetCheck.js` gains a line and arrow check.
- `showWidgetTool` hides a flawed first hand-drawn attempt and shows the second.
- `server/skills/builtin.js` gains `builtin:drawing`.

**Tech Stack:** Node ESM, no new dependencies. The repo's own test harness (`node test/<name>.test.mjs`). Playwright for the `ui-*` suites.

**Spec:** `docs/superpowers/specs/2026-11-17-diagrams-design.md`. Read the section each task names.

## Global Constraints

- **Limits on a `diagram`:**
  - at most 40 nodes and 80 edges;
  - `id` matches `/^[A-Za-z0-9_-]{1,40}$/` and is unique;
  - `title` is at most 60 characters;
  - `lines` is at most 6 entries of at most 80 characters;
  - at most 8 groups, never nested;
  - `direction` is `"right"` (the default) or `"down"`;
  - `kind` is `box` (the default), `pill` or `note`;
  - `style` is `solid` (the default) or `dashed`.
- **Layout figures:**
  - title 14 px bold, lines 12.5 px;
  - text widths use the same estimate as `widgetCheck`: 0.55 em per character, 0.6 em bold, 1 em per CJK character;
  - maximum box width 260 px with wrapping, minimum 120 px, padding 12 px;
  - rank gap 72 px (right) or 56 px (down);
  - node gap 24 px, and 40 px between groups;
  - group margin 16 px, canvas margin 24 px;
  - when the drawing is wider than 1,200 px it is scaled down through the `viewBox`;
  - 4 barycentre sweeps.
- **The line check:**
  - an arrow end counts as connected within 14 px of a box edge, a text box or another line's end;
  - a text within 18 px of a segment's midpoint is that segment's own label;
  - boxes overlap when they share more than 6 px and neither contains the other.
- **Adaptive diagram (added 2026-11-17, owner: "flexible adaptive smartest beautiful…"):**
  - `direction` defaults to `"auto"`. Lay out both directions and keep the one whose box is closer to 16:10, provided it fits 1,200 px at a scale of at least 0.8; otherwise keep the narrower one.
  - `theme` is `"light"` (the default) or `"dark"`.
  - `icon` is one of `user, server, database, cloud, cache, gear, document, chat, lock, chart, search, bolt`.
  - The look follows spec §"Adaptive and professional": tinted groups, white cards with a soft `feDropShadow` (6 % opacity, 1 px down, 3 px blur), an 8 px radius, a 1.5 px slate edge, a 7 px arrowhead, and labels at 11.5 px on a backing.
- **The design skills (spec §Layer 3 and §"Adaptive and professional"):**
  - There are five: `builtin:drawing` (about 7,000 characters) and four recipe families, `builtin:svg-flows`, `builtin:svg-structures`, `builtin:svg-sequences` and `builtin:svg-layouts` (about 9,000 characters each).
  - Each description is about 170 characters.
  - Every recipe gives: when to use it; a complete, valid SVG skeleton with `{placeholders}`; the placement arithmetic; adaptive rules (many items, long text, narrow screens, a dark canvas); the polish; and the pitfalls.
  - **Every filled skeleton passes `checkDiagram`**, line check included, at its comfortable size, at its adaptive extreme and on a dark canvas.
- **Redrawing:**
  - the redraw-once counter is `store.addToCounter('widget:redraw:<chatId>:<sha1(normalised title)>', 1, now + 30 min)`;
  - the normalised title is lower-case with its whitespace collapsed;
  - with no `chatId`, the drawing is shown at once;
  - a `diagram` is never hidden.
- **Copy:**
  - every new user-facing string goes in both `public/js/locales/en.js` and `vi.js`;
  - every sentence a person may see from the server goes in `server/i18n/vi.js`, and that includes every `new Error('…')` text (the gate's server-i18n check counts them all).
- **Code style:** comments say why. CODE-039 is at its ceiling of 93 back-to-back doc blocks: never put a `/** */` straight after another, and a section banner straight above a `/** */` counts, so leave a blank line between them.
- **Checks:** typecheck stays within baseline (ceiling 269), and lint is clean.
- **Line endings:** git stores LF and this machine checks out CRLF. Leave no mixed endings and no lone CR; check with Node before committing.
- **Never use `git stash`.** Stage by path. Never touch `.env`, `.env.example`, `.claude/`, `.vscode/` or `Exa Deep Research-3.4.1-v1/`.
- **Running tests:** run tests in the foreground. Implementers never run `npm run gate` or the full `npm run test:ui`. Python is broken here; use Node.
- **Commits** end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. If your attribution differs, use your own model's name.

### Task 1: Validate and lay out a diagram

**Files:**
- Create: `server/diagram/validate.js`, `server/diagram/layout.js`
- Create: `test/diagram.test.mjs`
- Modify: `package.json` only if the test runner chain needs the new file. Check how `npm test` lists suites, and add `node test/diagram.test.mjs` where similar suites are listed.

**Interfaces:**
- Produces `validateDiagram(input) → { ok: true, diagram } | { ok: false, error: string }`.
  - `diagram` is the input normalised: defaults filled, strings trimmed.
  - The error names what to change, for example `edge 3 goes to "gw", which is not a node id`.
- Produces `layoutDiagram(diagram) → { width, height, nodes, groups, edges }`:
  - `nodes`: `[{ id, x, y, w, h, title, lines: string[] (wrapped), kind, group }]`
  - `groups`: `[{ id, title, x, y, w, h }]`
  - `edges`: `[{ from, to, points: [[x, y], …], label, labelBox: { x, y, w, h } | null, style, reversed }]`
  - All coordinates are in the drawing's own units, before any scaling.

- [ ] **Step 1: Write the failing checks** in `test/diagram.test.mjs`, with the same harness shape as the other suites (`section`, `check`, `failures`, exit code). Cover:
  - **Validation:** each limit in the constraints is refused with a message naming it; unknown edge endpoints and duplicate ids are refused; the defaults are filled in.
  - **Layout:**
    - the same input gives deep-equal output twice;
    - no two node boxes overlap;
    - every edge's first point lies on its source box's border and its last point on its target box's border (within 0.5 px);
    - every segment is horizontal or vertical;
    - no segment crosses the inside of a box other than its own source or target;
    - no edge label box overlaps a node box;
    - a cycle A→B→C→A lays out, with exactly one edge marked `reversed`;
    - an edge from rank 0 to rank 3 passes no box;
    - a group's box contains all its members plus the 16 px margin;
    - `direction: 'down'` gives ranks that increase in y, not x;
    - 40 nodes and 80 edges lay out in under 200 ms.
- [ ] **Step 2: Run** `node test/diagram.test.mjs`. It fails, because the modules do not exist.
- [ ] **Step 3: Implement**, in this order:
  1. **Validate.**
  2. **Measure text** (one shared function, exported for render): wrap the title and lines to at most 260 px, then work out each box's width and height.
  3. **Break cycles** with a DFS in input order; reverse the back edges for layout.
  4. **Rank** by the longest path from the sources.
  5. **Insert dummy nodes** for edges that span more than one rank.
  6. **Order each rank:** start in input order, then do 4 barycentre sweeps (down, up, down, up). Keep each group's members contiguous by sorting on the group's mean barycentre, then the member's own.
  7. **Coordinates.** Ranks sit along the main axis, each rank's width the widest of its nodes, with the gaps from the constraints. Nodes sit along the cross axis, centred on the rank, with node gaps and the larger gap where the group changes. Run a simple pass that pulls a node toward its neighbours' mean where there is room.
  8. **Route edges at right angles.**
     - An edge leaves its source on the side facing the next rank, at a port spread evenly along that side.
     - It goes through each of its dummy positions.
     - It enters the target on the facing side.
     - In each gap between ranks, every edge that changes its cross coordinate gets its own lane.
  9. **Place labels** on the longest segment, sliding the label along the segment until it touches no box.
  10. **Group boxes:** the bounding box of the members plus 16 px, with room for the title.
  11. **Size** the drawing from the content plus the 24 px margin.
- [ ] **Step 4: Run** `node test/diagram.test.mjs`, `npm run lint` and `npm run typecheck`. All pass.
- [ ] **Step 5: Commit** `feat(diagram): a diagram is validated and laid out — ranks, dummies, barycentre order, right-angle edges`.

### Task 2: Render it, and draw it through `show_widget`

**Files:**
- Create: `server/diagram/render.js`
- Modify: `server/tools/cloud.js` (`showWidgetTool`), `server/tools/definitions.js` (the `show_widget` schema and its description)
- Test: `test/diagram.test.mjs` (render), and whichever suite covers `show_widget` today. Grep `show_widget` in `test/`.

**Interfaces:**
- Consumes `validateDiagram` and `layoutDiagram` from Task 1.
- Produces `renderDiagram(layout) → string`, an `<svg>` with:
  - `xmlns`, a `viewBox` and a `font-family: system-ui, sans-serif` style;
  - one `<marker>`;
  - group containers, nodes (`pill` with fully rounded ends, `note` lighter), edges as `<path d="M…L…">` with `marker-end` (dashed when `style: 'dashed'`), and labels on a canvas-coloured backing;
  - XML-escaped text.
- `show_widget` takes a `diagram` object.

- [ ] **Step 1: Write the failing checks.**
  - The render is well-formed: it parses as XML in Node, through a minimal check or by the shape of the output.
  - It escapes `<`, `&` and `"` in titles.
  - It contains exactly one `<marker>`.
  - Each edge's path matches its points.
  - `checkDiagram(renderDiagram(layout))` finds no issues for a 12-node fixture: the owner's 4-layer pipeline, rebuilt as a `diagram`.
  - `CLOUD_IMPLEMENTATIONS.show_widget({ title, diagram }, { userId, chatId })` returns a widget of kind `svg` and keeps it as a file.
  - A bad `diagram` returns the validation message as the tool's error.
- [ ] **Step 2: Run.** It fails.
- [ ] **Step 3: Implement** the renderer, and wire it into `showWidgetTool`.
  - Accept exactly one of `diagram`, `svg` or `html`, and refuse more than one.
  - Validate, lay out, render, then run `checkDiagram` (a problem is a layout bug: log it with `log.warn` without account data, and show the drawing anyway).
  - Keep the file as for a clean `svg`, and return `canvas: 'light'`.
  - In `definitions.js`, add the `diagram` JSON schema (nodes, edges, groups, direction, with the limits as `maxItems` and `maxLength` where JSON Schema allows).
  - Add one sentence to the description: use `diagram` for anything with boxes and arrows, `svg` for illustrations, and read the drawing skill.
  - Watch the token cost. The tool catalogue is paid for on every step, so keep the schema's descriptions short; see `.claude/skills/token-budget` if present.
- [ ] **Step 4: Run** `node test/diagram.test.mjs`, the `show_widget` suite, `node test/agent.test.mjs` (if the tool catalogue is checked there), `node test/server-i18n.test.mjs`, lint and typecheck. All pass.
  Extra, from spec §"Adaptive and professional":
  - extend `validateDiagram` to accept `direction: "auto"` (the default), `theme` and `icon`;
  - choose the direction automatically;
  - follow the look in the constraints, including both themes and the 12 icons;
  - test `auto` choosing `down` for a long chain and `right` for a wide, shallow one;
  - test that the dark theme keeps 4.5:1;
  - test that every icon renders and that an unknown icon is refused.
- [ ] **Step 5: Commit** `feat(diagram): show_widget draws a diagram the server lays out — auto direction, themes, icons`.

### Task 3: Check lines and arrows; a flawed hand drawing is redrawn once, unseen

**Files:**
- Modify: `server/widgetCheck.js` (new `checkLines`, joined into `checkDiagram`), `server/tools/cloud.js` (`showWidgetTool`)
- Modify: the client only if a hidden first attempt needs its own step label. If so, add the label to both locales, vi "Đang kiểm tra hình vẽ…".
- Test: `test/widget-check.test.mjs`, or the suite that covers `checkDiagram` today (grep it), plus the `show_widget` suite.

**Interfaces:**
- Produces `checkLines(markup) → string[]` (issues), included in `checkDiagram(...).issues`.

- [ ] **Step 1: Write the failing checks.**
  - **The owner's screenshot as a fixture:** arrows whose ends touch nothing, one through a text block, one through a box. Each gives its issue.
  - A box overlap is found.
  - A clean hand-drawn diagram finds nothing: arrows ending on box edges, labels beside them, a `<marker>`.
  - The Task 2 render finds nothing.
  - Lines inside a transformed `<g>` are skipped.
  - **Redraw once:**
    - A flawed first `svg` in a chat returns no widget and keeps no file; its content tells the model what is wrong and suggests `diagram`.
    - The second attempt with the same title returns the widget and keeps the file. Its content lists any remaining issues.
    - A `diagram` is never hidden.
    - With no `chatId`, the drawing is shown at once.
- [ ] **Step 2: Run.** It fails.
- [ ] **Step 3: Implement.**
  - **Parse** `<line>`, `<polyline>`, and `<path>` with `M/m/L/l/H/h/V/v/Z/z` into segments. A curve command counts only at its ends.
  - **Targets** an arrow may end on: `rect`, `circle`, `ellipse`, a closed `polygon` or `path` (taken by its bounding box, using the circle or ellipse itself for those), or a text box.
  - **Find arrows** by `marker-end`/`marker-start`, or by a small filled triangle whose tip is within 6 px of a segment's end.
  - **Run the checks** with the constraint thresholds. Use the box and text boxes `checkDiagram` already builds; refactor them so both checks share them, not copies.
  - **Word each issue** for the model, as the existing ones are worded.
  - **Redraw-once:** as in the constraints.
- [ ] **Step 4: Run** the check suite, the `show_widget` suite, `node test/diagram.test.mjs`, `node test/server-i18n.test.mjs`, `node test/i18n.test.mjs`, lint and typecheck. All pass.
- [ ] **Step 5: Commit** `feat(widget): lines and arrows are checked, and a flawed drawing is redrawn once before anyone sees it`.
